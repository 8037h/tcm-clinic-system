# 中医馆医师排班与绩效记录管理系统：技术说明

本文以当前仓库代码为依据，解释系统的结构、功能、关键业务规则和涉及的软件知识。它用于课程学习与项目交流；功能是否满足特定验收标准，应结合实际运行和测试结果判断。

## 一、系统做什么

系统面向中医馆排班、接诊与绩效记录的课程设计场景。管理员维护科室和医师，安排医师出诊，记录患者接诊情况，按医师和周期统计绩效，再通过查询、图表、日志和导出查看业务情况。

业务主线如下：

```text
科室 → 医师 → 出诊排班 → 接诊记录 → 按医师和周期汇总绩效
                  │             │
                  └─────────────┴→ 查询统计、图表、操作日志
```

绩效记录不直接保存接诊记录外键，而是按照医师和统计日期查询接诊记录，计算有效接诊数和完成数。系统还包含一个公开网页采集框架和采集数据列表。

## 四、Django 请求从哪里到哪里

1. 用户在浏览器访问 URL，或在表单填写数据并提交。
2. `tcm_clinic/urls.py` 和各 app 的 URL 配置将路径映射到视图。
3. 视图检查登录、角色权限以及用户能够看到的数据范围。
4. 查询页面使用 Django ORM 读取数据；提交页面通过 `Form` / `ModelForm` 和模型规则验证输入。
5. Django 将结果交给模板，生成 HTML；静态资源提供样式和图表。
6. 保存成功后使用 Django messages 展示反馈，并跳转到对应页面。

例如新增排班：进入排班表单 → 选择医师和时间 → 提交 POST → 检查时间先后与冲突 → 写入数据库 → 返回列表或详情。读取页面一般用 GET；删除和接诊、绩效状态变更使用 POST，提交表单时使用 CSRF 防护。

| --- | --- |

| `/login/`、`/logout/`、`/register/` | 登录、退出和普通用户注册 |

| `/departments/`、`/doctors/` | 科室和医师 |

## 五、数据库模型和关系

模型由 Django ORM 声明。`core/models.py` 定义科室、医师、排班、绩效、操作日志与采集数据，`receptions/models.py` 定义接诊记录。Django 还提供用户、权限、会话等内置表。

| 模型 | 主要字段 | 关系与用途 |
| --- | --- | --- |
| `Department` 科室 | 名称、介绍、启停状态、创建/更新时间 | 一个科室可关联多个医师 |
| `Doctor` 医师 | 用户、姓名、性别、年龄、电话、科室、职称、专长、简介、启停状态 | 可选地与用户一对一关联；外键指向科室 |
| `Schedule` 排班 | 医师、日期、开始/结束时间、最大和已预约人数、地点、状态、备注 | 外键指向医师；科室通过医师取得 |
| `ReceptionRecord` 接诊 | 患者基本信息、医师、可选排班、接诊时间、主诉、症状、诊断、治疗、处方、状态、备注 | 外键指向医师和可选排班；科室通过医师取得 |
| `PerformanceRecord` 绩效 | 医师、周期、接诊数量、完成数量、基础/奖励/扣减/总分、状态、审核信息、异常说明和附件 | 外键指向医师；审核人可关联用户 |
| `OperationLog` 日志 | 用户、模块、操作类型、对象、描述、IP、时间 | 用户可为空；部分日志关联具体绩效记录 |
| `CrawledMedicalData` 采集资料 | 标题、分类、症状、科室名称、来源名和 URL、发布时间、采集时间、正文 | `source_url` 唯一，用于去重 |

`ForeignKey` 表示多条记录可关联同一对象，例如多个排班关联同一医师；`OneToOneField` 用于用户与医师资料的一对一关联。排班及接诊的科室属性从 `doctor.department` 读取，减少重复存储。医师等受保护关系使用 `PROTECT`；接诊的可选排班被删除时使用 `SET_NULL`，接诊记录仍保留。

科室和医师状态为启用、停用；排班状态为正常出诊、停诊、已结束；接诊状态为待接诊、接诊中、已完成、已取消；绩效状态为待提交、待审核、已通过、已驳回、已确认。状态通过 Django `TextChoices` 表达。

## 六、主要业务功能

### 6.1 科室与医师

科室、医师提供列表、详情、新增、编辑、删除和每页 10 条分页。科室支持名称和状态查询；医师支持姓名、科室和状态的组合查询。删除使用确认页面，真正的删除操作使用 POST。医师详情页提供近期关联信息，便于查看业务链。

### 6.2 出诊排班

排班提供列表、详情、增删改、医师/科室/日期/状态查询和分页。`Schedule.clean()` 与 `has_time_conflict()` 实现基础规则：

- 开始时间必须早于结束时间。
- 同一医师、同一日期的正常出诊排班不能时间重叠；时间相邻可通过，例如 09:00—12:00 与 12:00—15:00。
- 已有关联接诊时，修改医师和时段不能与既有接诊产生不一致。
- 最大人数不能少于现有有效接诊数。

`remaining_slots` 以 `max(0, max_patients - booked_patients)` 计算剩余名额。

### 6.3 接诊记录与排班人数

接诊支持增删改查、详情、分页、CSV 导出，以及患者姓名、医师、科室、状态、开始日期和结束日期的组合查询。接诊可以不选排班；选择排班时，模型检查接诊医师与排班医师是否相同，时间是否处于排班日期及左闭右开的时间区间内，并检查排班是否正常、是否已满。

有效接诊不包括已取消记录。接诊保存、删除和取消等操作会同步关联排班的 `booked_patients`；已取消的不计人数。实现使用数据库事务和 `select_for_update()` 等机制，但默认 SQLite 不提供与支持行级锁数据库相同的并发保证，不能宣称已适合高并发预约。

接诊状态流转：

```text
待接诊 → 接诊中 → 已完成
   └───────────→ 已取消
接诊中 ─────────→ 已取消
```

完成接诊前必须填写诊断和治疗，处方可为空。状态变更通过 POST；已完成不能随意跳回待接诊。

### 6.4 绩效记录

绩效支持列表、详情、增删改、查询、分页、附件、状态操作和 CSV 导出。创建/普通保存、提交和管理员重新统计等路径会根据医师与周期计算：

```text
有效接诊数 = 指定医师、统计周期内未取消的接诊记录数
完成数     = 以上记录中状态为已完成的数量
总分       = 基础分 + 奖励分 − 扣减分
建议基础分 = 完成数 × 10（仅建议，不强制覆盖手工基础分）
```

周期按接诊时间的日期包含开始日与结束日。统计结果不是持续实时刷新的；接诊变化后可按权限和记录状态重新统计。开始日不能晚于结束日，完成数不能大于有效接诊数，基础/奖励/扣减分不能为负。

```text
待提交 ─┐
        ├→ 待审核 → 已通过 → 已确认
已驳回 ─┘      └→ 已驳回
```

提交时会重新统计并清空旧审核信息；审核通过或驳回时记录审核人和时间。当前代码中审核、确认由工作人员执行；新增、编辑、删除和重新统计有工作人员及状态限制。附件通过授权视图下载，访问会记日志。

## 七、账号、角色和权限

系统使用 `django.contrib.auth` 提供的用户、密码哈希、登录和会话。注册表单继承 `UserCreationForm`，普通用户注册后可登录；密码不以明文保存。部署运行时仍应使用合适的密钥和安全配置。

当前角色由 `core/permissions.py` 的规则判断：

- 工作人员：活跃且 `is_staff`，可按业务规则管理模块、审核绩效、查看分析和日志。
- 医师：用户关联到 `Doctor.user`；可查看本人医师资料、排班、绩效，并在授权范围内操作本人接诊和提交本人绩效。
- 普通登录用户：可访问获准的科室和公开采集资料，不能访问仅供管理员或医师的业务页面。

菜单和视图都参考权限规则；`scoped_queryset()` 对医师的数据范围进行筛选，接诊表单也限制可选医师和排班。当前设计属于代码内置的基础权限规则，不是可以通过界面配置任意角色、菜单和 API 的完整 RBAC 平台。实际权限行为应结合测试验证。

## 八、数据分析、概率与图表

`core/analytics.py` 使用 Django ORM 的 `Count`、`Q`、`Sum` 和 `TruncDate` 等汇总接诊、科室、医师、绩效和采集数据。首页展示医师、科室、今日排班/接诊、本月接诊、已完成接诊、待审核绩效、采集数据数量。

分析页包括最近 7 天接诊趋势、科室接诊、状态分布、医师接诊排行和医师绩效排行。后端将数据传入模板中的 JSON，`static/js/charts.js` 使用本地 ECharts 绘图；窗口变化时图表会调整大小，缺少图表脚本时有提示。

概率和统计是对已有记录的描述：

```text
完成比例 = 已完成接诊数 ÷ 全部接诊数
取消比例 = 已取消接诊数 ÷ 全部接诊数
某科室完成率 = 该科室已完成接诊数 ÷ 该科室接诊总数
```

分析总接诊分母包含所有状态，包括取消；与绩效中“有效接诊排除取消”的口径不同。无数据时，相关比例没有可用分母。每日均值、总体方差和总体标准差按最早至最晚接诊日期计算，中间无接诊的日期记为 0。医师排班数量和接诊数量的 Pearson 相关系数，仅在至少两个医师且两组数据均有变化时计算。历史比例和相关关系不等于预测或因果关系。

## 九、日志、导出与附件

`core/logging.py` 定义业务日志写入函数；登录由 `core/signals.py` 的 Django 信号处理，部分业务增删改、状态变更和附件访问由视图显式记录。日志包括用户、模块、操作、对象、描述、IP 和时间；管理员可以筛选和分页。日志并非对数据库一切修改的完整审计，例如部分 Django Admin 操作不一定进入这套业务日志。

接诊、绩效和分析等页面提供 CSV 导出，导出工具使用 UTF-8 BOM，并对以 `=`、`+`、`-`、`@` 等开头的值作处理以降低表格公式注入风险。下载和数据查询仍需对应权限。分析页面还提供浏览器打印入口；这不代表已实现 Excel 导出。

绩效附件默认存储在项目的 `private_uploads/performance/` 下，文件通过授权视图访问，不提供公共文件 URL。代码使用随机文件名；详见 `core/performance_storage.py`。

## 十、公开网页采集

采集框架使用 requests 和 BeautifulSoup，入口为：

```powershell
python manage.py crawl_medical_data
```

默认模式访问“中医世家”的中药学目录，先检查 `robots.txt`，使用正常 User-Agent 和请求超时，低频访问；目录和详情正文经过基本清洗，以 `source_url` 去重，单次最多处理 20 条，间隔至少 2 秒。请求失败会提示，未能可靠获取的字段不应编造。命令也支持通过 URL 和 CSS 选择器配置其他公开列表，规则和限制见 `core/crawler.py` 与管理命令源码。

目标站点是否可访问、结构是否仍匹配，需要实际运行时验证。此前出现过访问超时，仓库有采集框架并不等于已经成功获取中药材数据。

`research/` 中另有公开医师出诊资料的调研 CSV 及来源说明；它与中药材采集数据是两回事，也不会自动导入系统的排班或接诊表。

## 十一、数据库迁移与本地运行

Django 迁移文件记录数据库结构变更。下载项目后，安装依赖并执行 `manage.py migrate` 会在本机创建所需表；创建管理员后可启动开发服务器。具体 Windows 命令、下载方式和地址见 [README](../README.md)。

代码仓库不含本机数据库：其他人下载后得到的是源码，需要自己迁移、创建管理员及录入或准备数据。`127.0.0.1` 表示正在访问的那台电脑，不是可分享给他人的公网地址。Git/GitHub 用于同步代码，不会自动同步各电脑的 SQLite 文件和附件。

仓库包含单元测试文件，如 `core/test_schedules.py`、`core/test_access_workflow.py` 和 `receptions/tests.py`。有测试文件不代表所有业务已经通过最终验收；运行环境、迁移状态和实际测试结果均需要单独核验。

## 十二、在线演示与实际部署边界

项目曾使用 ngrok 将本机独立演示数据库的 Django 服务作为临时公网演示。此类链接依赖运行机器、网络和转发进程保持开启；GitHub 仓库本身不会运行 Django。独立演示数据与真实业务数据用途不同，不应将模拟内容描述为真实医疗记录。

`demo_settings.py` 为演示数据库和绩效附件设置了独立路径。绩效附件存储使用 `PERFORMANCE_STORAGE_ROOT` 作为可选根目录；默认项目沿用原项目根目录，演示环境使用 `demo_public`。公开演示账号的访问者会共同操作演示数据。

默认 `settings.py` 提供开发用途的默认密钥并默认开启 DEBUG，默认数据库为 SQLite，`runserver` 用于开发。真实部署前需要重新设计并验证生产配置、密钥、数据库、并发、备份、日志、权限、附件和隐私保护；本课程项目不应直接用于真实医疗业务。
